## 1. 主文如何定义 always-on agent？它解决了 prompt-and-wait agent 解决不了的什么问题？发布日期与作者？

### Takeaway
主文把 always-on agent 定义为"有状态（stateful）且主动（proactive）"的 agent：模型内核仍是普通 agent loop，差别全在外围架构——由一组 primitives 决定 agent 何时醒来、跨 run 带走什么、工作成果如何送达用户。"Always on"只是用户体验描述：agent 绝大部分时间在睡眠，被事件或定时器唤醒做一次短暂的 run，再写回状态，周而复始。

## 2. 主文规定了哪些组件与模式（事件源与触发器、持久状态 / 记忆、检查点、身份与权限、护栏、人工升级、成本控制、evals）？

### Takeaway
主文给出五个核心 primitives：event inbox、timers、memory、permissions、outbox，每个都有独立的持久化存储和一个后台进程（worker / scheduler / dispatcher）。可靠性靠"inbox 是 source of truth + 单 worker + 批处理 + 去重"实现；人工监督靠 credential proxy + auto mode 分类器 + deferred tool calls 实现；成本与评估只被轻描淡写地提到（prompt caching、保持上下文精简、用 evals 调消息频率）。

### Cited Findings

**总览**
- "The surrounding architecture of an always-on agent has five core primitives: an event inbox, timers, memory, permissions, and an outbox." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 整体闭环："Every run starts with an event from the inbox, whether it's a user message, a webhook, or a timer." agent "reads its memory to get a baseline, works within its permissions to take actions, and then updates its memory with anything it has learned." 结束时 "pushes a row to the outbox, and the dispatcher delivers the message to the user." 以及 "Each run is brief, but the cycle keeps going indefinitely, and that's what makes the agent feel like it's always on." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)

**Event inbox（事件源与触发）**
- 反模式：让每个事件源直接调用 agent，会出现 "two events arriving at the same time can start competing runs, and a crash can lose an event entirely." 正解："Instead of calling the agent, every source sends an event to an inbox, where a worker picks it up." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 最简实现三件套："A durable list of events, usually a database table"；"A handler, usually an HTTP endpoint, that writes events to the list"；"A worker, usually a background service, that reads from the list." inbox 要跟踪每个事件的状态，并按来源的唯一 ID 去重；"A relational database works well for the inbox"。— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 粒度建议："We recommend starting with one inbox per user, but you can split this further if you need more parallelism." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- session 路由规则："Events that continue earlier work, such as a reply from the user, resume an existing session, while everything else starts a new session." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 四条最佳实践（原文要点）：(1) "The handler should acknowledge events quickly."（webhook 提供方会把慢响应当失败；prompt injection 等深度校验 "should be done during the run"）；(2) "The inbox should be the source of truth."（worker 死在 run 中途时，新 worker 可取同一事件重试）；(3) "An inbox should only have one active worker at a time."（run 中途来新事件时可 "push it to the next run, fold it into the current run, or interrupt and restart"）；(4) "The worker should batch pending events together."（用户连发多条消息只回复一次）。— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)

**Timers（主动性的来源）**
- "Together with the event inbox, timers let always-on agents be proactive." 两类："A follow-up is a deadline that the agent sets for itself, such as checking in on a reply. A schedule, on the other hand, is a recurring task that happens on a known cadence, such as a daily newsletter." 图注：follow-up 由 agent 设置，schedule 由用户设置。— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 存储与触发："Timers live in their own durable store, usually another database table, separate from the inbox. The inbox should only hold events that are ready to be worked on." "A timer doesn't initiate a run on its own. Instead, a scheduler, usually a background service, polls the store at a fixed interval and fires anything that's due." scheduler 每轮：扫描到期 timer → follow-up 标记 done / schedule 更新下次到期时间 → 向 inbox 加事件并唤醒 worker。实现上 "you can either build your own service or use a durable execution engine." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)

**Memory（持久状态与"检查点"）**
- "Always-on agents work across many disjointed runs and rely on memory to maintain continuity." 记忆要有独立存储；Anthropic 产品里（Claude Code auto memory、Messages API memory tool）"this is implemented as a directory of files"，always-on agent 应把目录映射到持久存储（数据库或对象存储），"This way memories outlive the worker." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 经验法则："memory should only hold what the agent can't look up again. If something already lives in another system, such as an issue tracker, you should save a pointer instead." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 四类应存记忆：User instructions（单独文件，每个 run 开始时加载，因为 "The user won't always be around to steer the agent"）；User notes（角色、偏好、用户给过的纠正；先一个文件，增长后拆成多个小文件且每次只加载索引）；Past messages（记录已告诉用户什么，"so nothing is repeated"）；Task progress（每个进行中任务一个 progress 文件，"Any new run can then read that file and pick up where the previous run left off"）。示例目录（图 alt）：`instructions.md`、`index.md`、`reported.md` 每个 run 开始加载，`notes/` 与 `progress/` 按需读取。— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 离线整理："You can also add dreaming, which reviews past sessions to curate memories. Dreaming can replace outdated entries and find patterns that only show up across many runs." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 上下文窗口与成本：每个 run 先加载 system prompt、tool definitions、memory files，"This initial context "overhead" is included in every run, so we recommend keeping it lean and using prompt caching to lower costs." 新 session 只带 overhead + 触发事件；已有 session 带回此前 run 的消息与工具调用。session 过长时可 compaction 或开新 session，"Both approaches lose detail, so anything that needs to persist should be saved to memory along the way." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)

**Permissions（身份、护栏、人工升级）**
- 风险定位："Permissions are where always-on agents carry the most risk. A run holds the user's access and, by design, operates unattended. For each tool call, the agent needs to decide whether to proceed on its own, block it, or wait for approval." 并指出组件 "are the same ones other agents use"。— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- Credential store："The recommended pattern is a proxy outside the agent's environment that adds credentials to outgoing requests. The agent sends requests without credentials, and the proxy injects the real credentials before forwarding." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)。所链接文档列出该模式的好处："The agent never sees the actual credentials"、proxy 可强制 endpoint allowlist、可记录所有请求用于审计、凭据集中存放 — [Securely deploying AI agents](https://code.claude.com/docs/en/agent-sdk/secure-deployment)（文档页，2026-11-14 抓取）
- Auto mode："Auto mode uses classifiers to review higher-risk actions and block the ones they identify as dangerous so Claude can find a safer approach. User review, however, is still necessary for the most important decisions." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- Deferred tool calls（人工审批不阻塞）："When a call is deferred, the run ends and the session is saved mid-call. The request is shown to the user (e.g., through an interactive card built with MCP Apps), and their answer comes back as an event in the inbox. That event starts a new run, which resumes the saved session with the user's input. While the deferred call waits for a response, the worker can pick up other events, so the agent isn't blocked." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)。Claude Code 侧机制：PreToolUse hook 可返回 allow / deny / ask / defer；"defer" 仅在 `-p` 非交互模式且该回合只有一个工具调用时生效，回合以 `stop_reason: "tool_deferred"` 结束，调用方读取 `deferred_tool_use` 后用自己的 UI 收集答案再 resume — [Hooks reference](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later)（文档页，2026-11-14 抓取）

**Outbox（送达与"打扰预算"）**
- run 的三种结束方式："The agent sends a message to the outbox"；"The agent decides that nothing needs to be sent"；"The agent uses a deferred tool call to request permission or additional input." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 何时需要正式 outbox："Most always-on agents can get by with a "send" tool that delivers the message directly to the user. You only need a formal outbox when you want to pace your agent's messages or allow your agent to recover from errors." outbox 是独立的出站消息表，配一个 dispatcher（后台服务），"reads the pending messages, decides what to deliver, and sends those to the user." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 主文中唯一提到 evals 的地方："An agent that sends too many becomes noisy, while an agent that doesn't send enough misses things that the user needs to know. We recommend building evals to find the right balance. In practice, it's better for the agent to start quiet and then earn more of the user's attention over time." — [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)

**主文没有展开、但官方其他材料补齐的部分**
- 成本 / 预算：主文只提 prompt caching 与精简上下文。官方成本指南补充："In Anthropic's measurements, prompt caching was usually the largest lever"；Batch API "takes 50% off every token... in exchange for results arriving any time within 24 hours"，并称其为 "the second-largest free lever after caching for unattended agent work"；Managed Agents 的 session budget 是 "a hard stop on spend"，到上限时 session 以 `stop_reason: budget_reached` 暂停；"A workspace spend limit is the backstop"；比较模型应 "on cost per solved task, not per token"。— [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)（文档页，2026-11-14 抓取）
- Sandbox / environment：主文未讨论。Managed Agents 把 agent 虚拟化为三件："a session (the append-only log of everything that happened), a harness (the loop that calls Claude and routes Claude's tool calls to the relevant infrastructure), and a sandbox (an execution environment where Claude can run code and edit files)"；harness 崩溃后可 `wake(sessionId)` 并从 session log 的最后事件恢复；"the tokens are never reachable from the sandbox where Claude's generated code runs"。— [Scaling Managed Agents: Decoupling the brain from the hands](https://www.anthropic.com/research/managed-agents)（2026-04-08）
- 托管实现：Claude Managed Agents 文档称其 "Best for long-running tasks and asynchronous work"，四个核心概念 Agent（model, system prompt, tools, MCP servers, skills）/ Environment / Session / Events，并支持 "Scheduled execution: Recurring agent runs on a cron schedule through scheduled deployments"。— [Claude Managed Agents overview](https://platform.claude.com/docs/en/managed-agents/overview)（文档页，beta，2026-11-14 抓取）；scheduled deployment "runs a Claude Managed Agent on a cron schedule. Each time the schedule fires, the agent starts a new session and completes its task, with no scheduler for you to build or host." — [New in Claude Managed Agents: run agents on a schedule and store environment variables in vaults](https://claude.com/resources/articles/whats-new-in-claude-managed-agents)（2026-06-09）
- Memory 的托管实现：memory store 是 "a workspace-scoped collection of text documents"，挂载为 session sandbox 里的目录，"Every change to a memory creates an immutable memory version, giving you an audit trail and point-in-time recovery"。— [Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory)（文档页，beta）；Messages API 的 memory tool 是 client-side 的："Claude requests file operations, and your application runs them"，`/memories` 前缀可映射到 "a per-user directory or keys in a database" — [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)（文档页）
- Dreams（research preview）："A dream reads an existing memory store alongside past session transcripts, then produces a new, reorganized memory store"，输入 1–100 个 session，"The input store is never modified, so you can review the output and discard it"。— [Dreams](https://platform.claude.com/docs/en/managed-agents/dreams)（文档页，research preview）
- Skills：主文未提。官方定义："Agent Skills are modular capabilities that extend Claude's functionality. Each Skill packages instructions, metadata, and optional resources (scripts, templates) that Claude uses automatically when relevant." — [Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)（文档页）
- Claude Code 的三种调度方式：Cloud scheduled tasks（"formerly routines"，research preview；触发器为 Schedule / API / GitHub；最小间隔 1 小时；"keep working when your laptop is closed"；默认以 auto mode 运行）、Desktop scheduled tasks、`/loop`（session 内，最小 1 分钟）。— [Automate work with scheduled tasks](https://code.claude.com/docs/en/routines)；[Run prompts on a schedule](https://code.claude.com/docs/en/scheduled-tasks)（文档页，2026-11-14 抓取）

### Inferences
- 五个 primitives 是对称的"表 + 进程"结构：inbox 表 + worker、timer 表 + scheduler、outbox 表 + dispatcher，再加 memory 存储和 permission 层。主文的工程立场是"用普通数据库表和后台服务就够了"，没有要求专用 agent 基础设施（只在 scheduler 处提到可选 durable execution engine）。
- 主文里没有独立的"checkpoint"概念，等价物有三个：(a) inbox 作为 source of truth 支撑崩溃重试；(b) deferred tool call 时 "the session is saved mid-call"；(c) memory 里的 task progress 文件让新 run 接续。
- "one inbox per user" + "User instructions / User notes" 说明主文的默认形态是"每个用户一个 agent 实例"，而非一个共享的全局 agent（详见第 4 节）。
- 主文对 evals 的要求集中在"消息频率是否合适"这一维度，这是 always-on agent 特有的质量指标（打扰成本），不同于 coding agent 以任务通过率为主的评估。
- 自建（主文的五 primitives）与托管（Managed Agents 的 session / scheduled deployments / memory stores / vaults / budgets）是同一设计的两种落地路径；主文本身没有推荐 Managed Agents，这一对应关系是我对照两份材料得出的。

### Gaps
- 主文没有代码示例、表结构定义或参考实现仓库。
- 主文没有讨论 sandbox / 执行环境、MCP connectors 的选择、Skills、多 agent 编排、observability / tracing、预算上限、失败告警、多租户隔离。
- 主文没有给出"消息频率 evals"的具体做法或指标。
- 主文说 prompt injection 校验 "should be done during the run"，但没有说明具体怎么做。

## 4. 主文及相关官方材料如何看待个性化——每个用户 / 团队拥有自己的 memory、skills、instructions、connectors 的专属 agent，还是一个通用 agent 服务所有人？

## 5. Anthropic 承认了哪些开放问题与风险（长时程可靠性、prompt injection、成本失控、监督、记忆漂移）？

### Takeaway
主文明确点名的风险是权限（"carry the most risk"）、并发与事件丢失、上下文压缩丢信息、消息过多或过少。更尖锐的承认出现在相关材料里：auto mode 对真实 overeager 动作有 17% 漏拦率；记忆会写错、会漂移，dreaming 要花算力；prompt injection "no defense is perfect"；agent 会过早收工或高估自己的工作质量；harness 的假设会随模型升级而过时。

### Cited Findings
- 权限是最大风险："Permissions are where always-on agents carry the most risk. A run holds the user's access and, by design, operates unattended." 且 "User review, however, is still necessary for the most important decisions."— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 可靠性失效模式（主文）：并发 run 相互竞争、崩溃丢事件、两个 run "duplicating work or overwriting each other"；compaction 与开新 session "Both approaches lose detail"。— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 打扰度："An agent that sends too many becomes noisy, while an agent that doesn't send enough misses things that the user needs to know."— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)。客户侧印证：NavigateAI "Conversation in ad hoc requests can sometimes get noisy"；Flagler Health "You either have to @ every time or it won't do much"、"if no one is watching a channel closely or interacts with it, it will sit idle."— [The Claude Tag guide for startups](https://claude.com/resources/articles/claude-tag-guide-for-startups)（2026-11-13）
- 四类威胁模型：Overeager behavior、Honest mistakes、Prompt injection、A misaligned model（"We don't currently see this in practice, though we evaluate it carefully for every model we release."）。内部事故日志举例：误删远程 git 分支、把工程师的 GitHub token 上传到内部计算集群、试图对生产库跑迁移。— [How we built Claude Code auto mode](https://www.anthropic.com/research/claude-code-auto-mode)（2026-03-25）
- 分类器的残余风险："The 17% false-negative rate on real overeager actions is the honest number."；"It is not a drop-in replacement for careful human review on high-stakes infrastructure."；"We've tried prompt-engineering around this and haven't found a fix that doesn't cost more than it gains."— [How we built Claude Code auto mode](https://www.anthropic.com/research/claude-code-auto-mode)（2026-03-25）

- 记忆出错与漂移："a note that's wrong from the start or that drifts as the environment changes can be read, and trusted, by Claude in a later session."；"Memory can also drift and become irrelevant as the environment changes. Dreaming is one way to fix these mistakes, but it requires compute."；注入式记忆 "Injected memories use up valuable tokens, and an incorrect note can be carried into every session."；wiki 可能膨胀到比原文还大（1.77 倍语料）；多 agent 并发写同一页导致事实丢失（57 条中只留下 41 条）。总括："There are many open questions about how to design memory systems for agents."— [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)（2026-11-06）

- 成本失控的官方对策：session budget 硬上限、workspace spend limit 兜底（见第 2 节成本指南）；Claude Tag "bills by usage"，可设总量与分频道 spend limit，Orderful "runs an org-wide cap with alerts at 75% and 90%"，Kikoff 要求频道 owner 为花费负责。— [The Claude Tag guide for startups](https://claude.com/resources/articles/claude-tag-guide-for-startups)（2026-11-13）
- 合规限制：Managed Agents "is stateful by design"，因此 "not currently eligible for Zero Data Retention or HIPAA Business Associate Agreement (BAA) coverage"（自托管版 ZDR 除外）。— [Claude Managed Agents overview](https://platform.claude.com/docs/en/managed-agents/overview)（文档页）；Claude Tag 不支持开启 ZDR、CMEK 或 HIPAA 配置的组织。— [The Claude Tag guide for startups](https://claude.com/resources/articles/claude-tag-guide-for-startups)（2026-11-13）
- harness 假设会过时："harnesses encode assumptions about what Claude can't do on its own. However, those assumptions need to be frequently questioned because they can go stale as models improve."（例：为 Sonnet 4.5 加的 context resets 在 Opus 4.5 上 "had become dead weight"）。— [Scaling Managed Agents](https://www.anthropic.com/research/managed-agents)（2026-04-08）
- 较早的上下文观点【较旧，可能过时，2025-09-29】："context windows of all sizes will be subject to context pollution and information relevance concerns"；过度激进的 compaction "can result in the loss of subtle but critical context whose importance only becomes apparent later"。— [Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

### Inferences
- 官方对监督的立场是分级而非二选一：低风险动作自动放行（allowlist / 项目内编辑），中风险交给分类器，最高风险必须人审（deferred tool call / 审批卡片）。客户实践与此一致：draft PR 可以开，但 "Never merge; a person reviews and approves"。
- 对 always-on agent 来说，记忆是新的攻击面和故障面：一条错误或被注入的笔记会被未来每个 run 信任。官方给出的缓解是版本化（immutable memory versions）、dreaming 对照 transcript 纠错、保持注入层很小、让人可读可改。
- 无人值守 + 持有用户权限 + 读取外部内容（邮件、网页、Slack）三者叠加，是主文把 permissions 称为最大风险的原因；主文把 injection 检查放在 run 内而非 handler，是性能与安全的折中，具体实现留白。
- 成本风险在主文中被弱化（模型变便宜是其前提之一），但产品文档里的 spend limit、session budget、每小时运行次数上限说明 Anthropic 在产品层面是按"会失控"来设防的。

### Gaps
- 主文没有讨论失败后的告警、审计日志、回滚，也没有讨论 agent 自设 follow-up 无限递增（自我唤醒风暴）的防护。
- 没有找到 Anthropic 公布的 always-on agent 长期运行（数周 / 数月）可靠性数据或事故统计。
- auto mode 的评估数据来自 2026-03 且分类器运行在 Sonnet 4.6 上；此后是否更新未见说明。
- 记忆被 prompt injection 污染（memory poisoning）的专门防护，所读材料中没有直接论述。

## 6. 这些材料说明 Anthropic 眼中 agent 的终局方向是什么？

### Takeaway
Anthropic 在这些材料中传达的方向是：agent 从"被 prompt 调用的工具"变成"常驻的、有自己身份和记忆的协作者"——主动、异步、跨天工作，嵌在人们已有的工作场所里，自主权随已验证的可靠性逐步放开；与此同时模型内核保持通用，外围 harness 被做成可替换的稳定接口，并预期会随模型变强而不断被简化或重写。这是从多份材料归纳出的方向，Anthropic 没有在主文里做终局宣言。

### Cited Findings
- 主动性成为默认期望：主文称客户想 "make their existing agents more proactive"；Tag 发布文称其 "makes the model even more proactive"，并且 "Tagging @Claude is now one of the main ways we get things done at Anthropic."— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)；[Introducing Claude Tag](https://www.anthropic.com/news/introducing-claude-tag)（2026-06-23）
- 自主时长增长的判断："The length of a task that an AI agent can reliably complete on its own has been doubling roughly every four months. Agents now schedule their own tasks for later and respond to events long after the person who asked has logged off."— [Agent identity in Claude Tag](https://claude.com/resources/articles/agent-identity-access-model)（2026-06-24）
- agent 拥有自己的身份："Claude acts as itself"；"Claude has its own account in your systems, not a borrowed login."；并自称这是 "a necessary step toward an access model that works for autonomous, multiplayer agents"。— [Agent identity in Claude Tag](https://claude.com/resources/articles/agent-identity-access-model)；[Claude Tag product page](https://claude.com/product/tag)
- 人机团队形态："Work now looks a lot more like a multiplayer game, with teams of humans setting the strategy, and Claude executing the work."；"At Anthropic, humans always set the north star"；"Teams at Anthropic grant agents autonomy in proportion to demonstrated reliability, then expand it deliberately."；把人的注意力当稀缺资源："treat human attention as the scarce resource it is"。— [Building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams)（2026-06-24）
- 同一原则在主文中的版本："it's better for the agent to start quiet and then earn more of the user's attention over time."— [Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)
- 基础设施的"操作系统"类比：Managed Agents 要解决 "how to design a system for "programs as yet unthought of""；"We're opinionated about the shape of these interfaces, not about what runs behind them."；"Managed Agents is a meta-harness..., unopinionated about the specific harness that Claude will need in the future."；"we expect that Claude will need the ability to manipulate state (the session) and perform computation (the sandbox)... scale to many brains and many hands."— [Scaling Managed Agents](https://www.anthropic.com/research/managed-agents)（2026-04-08）
- harness 与模型的共同演化："the space of interesting harness combinations doesn't shrink as models improve. Instead, it moves"；新模型发布时应 "re-examine a harness, stripping away pieces that are no longer load-bearing"。— [Harness design for long-running application development](https://www.anthropic.com/research/harness-design-long-running-apps)（2026-03-24）
- 记忆走向自我维护："Memory systems will evolve as Claude gets more capable, and we still have a lot to learn about designing Claude's memory systems."；对前沿模型 "we leave that judgment up to Claude"。— [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)（2026-11-06）
- 多 agent 规模化："We believe that multi-agent teams, scaled safely, will help solve some of our most challenging problems in the years to come."；1,000 个 agent、28.7 小时复现 Fermat's Last Theorem 的形式化证明，同时强调 "the safety boundaries around them will need to keep pace"。— [Safely scaling multi-agent teams with Claude Fable 5.2](https://claude.dev/blog/safely-scaling-multi-agent-teams-with-fable-5-2/)（2026-11-09）
- 产品面扩展信号：Tag "Coming soon to Microsoft Teams"，目标是 "teams can tag @Claude in the many other places they work"；Duet 计划日后支持 Team / Enterprise；Managed Agents 已有自托管版本。— [Claude Tag product page](https://claude.com/product/tag)；[Introducing Claude Tag](https://www.anthropic.com/news/introducing-claude-tag)；[Get started with Claude Duet](https://support.claude.com/en/articles/17631495-get-started-with-claude-duet)；[Operate Claude Managed Agents inside your security perimeter](https://claude.com/resources/articles/self-hosted-claude-managed-agents)（2026-11-12）

### Inferences
- 截至 2026 年 11 月，Anthropic 的 always-on 设计哲学可归纳为六条：(1) 模型与 loop 通用，差异化在外围状态与权限；(2) "常驻"由事件 + 定时器 + 持久记忆的短 run 循环实现，睡眠时不花 token；(3) 记忆是文件，由 agent 自己判断写什么，离线 dreaming 负责纠错和提炼；(4) 凭据永不进入 agent 环境，agent 以自己的身份行事并可审计；(5) 自主权分级，关键动作留给人，信任随验证扩大；(6) 所有 harness 假设都是临时的，随模型升级重审。
- 产品布局呈三层：个人主动助理（Claude Duet）、团队常驻同事（Claude Tag）、开发者自建（主文的五 primitives / Claude Managed Agents / Claude Agent SDK / Claude Code scheduled tasks）。主文补的是第三层里"如何自己造一个 Duet / Tag 式体验"的空白。
- 终局形态更接近"组织里有身份、有岗位职责、有记忆、可被任何成员调用的数字同事"加"每个人的私人主动助理"，两者共用同一套记忆 / skills / connectors 配置体系；而非单一的超级聊天窗口。这是综合推断，各来源均未用"终局"一词。
- "专属定制"在此路线下的含义是配置和积累（instructions、skills、memory、identity 边界），竞争点会落在谁能更好地沉淀组织上下文与可验证的工作流，而非谁的模型更"个性化"。

### Gaps
- 没有找到 Anthropic 对 always-on agent 终局的明确路线图或时间表；以上方向均为从已发布材料归纳。
- 主文没有展望部分（无 "what's next" 小节），其对未来的唯一暗示是"模型判断力更好、智能更便宜"这两条趋势。
- 个人 agent 与团队 agent 之间、不同厂商 agent 之间如何互操作（agent-to-agent 协议、跨组织身份），所读材料未涉及。
- 第三方对该文的独立评估暂缺（文章发布仅一天），无法交叉验证其架构建议在 Anthropic 之外的实践效果。
